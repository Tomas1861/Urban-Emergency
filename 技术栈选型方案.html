整体技术栈选型方案

延续《Ontology基座技术方案》的选型原则：3人研究生团队、一年期、49万经费，优先选"团队学得快、部署运维简单"的技术，不追求业界最佳实践——如果那意味着额外的运维负担。能用现有代码库已经在用的技术解决的问题，不引入新组件。

一、数据库：三种能力，不需要三个数据库服务

1.1 关系数据存储 —— 继续用 SQLite，何时切换 PostgreSQL

现状：backend/yingji_mvp.db（SQLite），SQLAlchemy + Alembic。三个月冲刺阶段维持 SQLite 不动——单机、免安装、Alembic 迁移脚本不用改。

需要切换到 PostgreSQL 的时机：教学实验台上线、多组学生并发写入的时候。SQLite 在多进程并发写入时会有锁等待问题，教学场景一旦有 5+ 组学生同时点"运行实验"，会明显卡顿。切换成本不高——SQLAlchemy 已经做了数据库无关的抽象，只要现有代码没用 SQLite 专属语法，改一下 DATABASE_URL 和 Alembic 配置就行，不需要重写模型。

不建议：现在就上 PostgreSQL。规模没到，徒增本地开发和部署的环境依赖。

1.2 知识检索 —— 不引入独立向量数据库

需求重构稿要求的"知识检索"，技术上分两档，建议从第一档开始：

第一档 · 三个月冲刺就做 关键词检索。用 rank_bm25 对已解析的文档片段做 BM25 检索，不需要任何 embedding 模型、不需要向量数据库。对应真实限制——rag_service.py 现在返回空，先把这一档跑通，就已经比"返回空"是质的提升。
第二档 · 三个月之后 本地开源中文 embedding 模型（BGE系列，用 sentence-transformers 跑，免费）算向量，用 sqlite-vec（SQLite）或 pgvector（已切Postgres）存和查——都是"在现有数据库上加扩展"，不是新增服务。
明确不建议 Milvus、Weaviate、Pinecone 这类专用向量数据库——是给"千万级向量、独立检索集群"场景用的，教学项目知识库大概率几十到几百篇文档，用不上，还平白多一个要学、要运维的服务。

1.3 图数据库 —— 不用（已装的 Neo4j 驱动可以先不接）

理由同《Ontology基座技术方案》：对象规模小，关系查询用 SQL JOIN 够用。除非以后真的出现需要多跳图遍历的复杂查询，否则不需要图数据库。

1.4 后台任务调度 —— 用 APScheduler，不需要 Celery + Redis

需求重构稿 14.3 节要求的"状态变化与待发送事件一并可靠保存，由后台任务投递"，典型场景是"效果监测的观察窗口超时检测"。

建议：APScheduler，跑在 FastAPI 同一个进程里，配置一份定时任务定期扫描"观察窗口已过期但未达标"的方案。不需要额外部署 Redis 和 Celery worker。

升级时机：任务量大到单进程定时扫描处理不过来（教学实验台多组并发触发大量偏差检测）时，再引入 Celery + Redis。三个月冲刺阶段用不到。

二、AI 能力：LLM、Embedding、Agent 编排

2.1 大模型 API 选型

llm_service.py 目前未接入。选型考虑三点：中文效果、结构化输出（function calling / JSON mode）能力、成本。

候选 · 优先考虑 国产 API（通义千问、DeepSeek、智谱 GLM-4 等）：性价比高，中文语境效果好，国内网络直接可用，教学演示场景不需要顶级模型能力。
候选 · 备选 OpenAI / Claude API：效果更好，但成本更高，且需要考虑网络访问的稳定性——如果已有可用渠道，也是合理选择。

硬性要求：无论选哪家，必须支持结构化输出（function calling 或 JSON mode）——需求重构稿反复强调"模型不能自行改写结果"，这不是靠 prompt 里写"请输出JSON"就能可靠保证的，要用 API 原生的结构化输出能力。

2.2 Embedding 模型

见上文 1.2 第二档：本地开源模型（BGE 系列），跑在自己的机器上，不调用付费 embedding API——一年期项目如果知识库要反复重新索引，调用付费 embedding API 的成本会累积，本地模型是控制成本的具体一点。

2.3 Agent 编排 —— 不引入 LangChain / LangGraph 类框架

建议 直接用所选大模型 API 的原生 tool use / function calling，配合团队自己写的 Python 控制流程（backend/app/agents/ 现有结构就是这个思路，继续沿用）。
为什么不用重型框架 抽象层多，出问题时不好调试。需求重构稿要求"运行控制器由程序负责……不能用'多个Agent都赞同'替代规则引擎"——自己写清楚的状态机，比塞进通用框架的抽象里更可控、更容易审计。

这也是需求重构稿引用的 Anthropic《Building effective agents》一文的核心建议：优先用简单、可组合的模式，不要一开始就上框架。

三、后端框架 —— 现状已经合适，不需要换

FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic（backend/pyproject.toml）已经是这个项目规模的合理选择：FastAPI 的类型系统和自动文档天然适合"结构化输入输出"这种需求密集的场景，Pydantic 的校验正好用来约束 Agent 的结构化输出格式。不需要引入任何新的后端框架组件，接下来的工作是在这套骨架里把模型、服务、Agent 填充完整，不是换地基。

四、前端框架 —— 现状已经合适，不需要换

Vue3 + Element Plus + Pinia + Vite（frontend/）同理，不需要新增技术栈。教学实验台、本体对象视图这些新页面，按现有的 views/ 组织方式继续加就行。

五、测试策略

后端已有 pytest 依赖。补充两类当前缺失的测试：

  • Agent 测试用 mock 大模型响应，不要在自动化测试里真的调用 LLM API（慢、花钱、结果不确定）。给 llm_service.py 加一层可替换的接口，测试时注入固定返回值，验证的是"Agent 拿到这个返回值后，状态流转对不对"，不是"模型这次答得好不好"。
  • 本体服务的边界场景测试：别名歧义时是否正确返回歧义列表而不是擅自选一个、证据过期时是否正确拒绝把状态当已确认用——这两条直接对应 AC01、AC02，写成自动化测试比每次人工点一遍界面可靠。

六、部署

Docker Compose 足够：一个 backend 容器 + 前端构建产物用 Nginx 或简单静态服务器托管（若切换 PostgreSQL 再加一个数据库容器）。不需要 Kubernetes——这个规模的教学演示系统上 K8s 是纯粹的运维负担，没有对应的收益（不需要自动扩缩容、不需要多可用区）。
